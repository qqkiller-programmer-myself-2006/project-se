# งานวิจัย API ตรวจสอบสลิปและ PromptPay สำหรับร้านป้าอ้ออาหารตามสั่ง

อัปเดตข้อมูล: 12 กันยายน 2569 (2026)

## สรุปคำแนะนำ

สำหรับโครงงานรุ่นแรก แนะนำให้ใช้ **EasySlip API v2 แพ็กเกจ Start** เป็นตัวตรวจสอบสลิปอัตโนมัติ และมี **Admin ตรวจด้วยมือเป็น fallback** เมื่อ API ใช้งานไม่ได้หรือผลตรวจไม่สมบูรณ์ เหตุผลคือราคาเริ่มต้นที่ประกาศชัดเจนเพียง 99 บาท/30 วัน สำหรับ 250 ครั้ง รองรับการส่ง QR payload/รูป/Base64/URL ตรวจสลิปซ้ำ ตรวจบัญชีผู้รับ และตรวจยอดเงินได้ จึงเหมาะกับการทดลองระบบของร้านเดียวและมีเอกสารสำหรับนักพัฒนาค่อนข้างครบ ([ราคา EasySlip](https://easyslip.com/api-products/), [เอกสาร EasySlip API v2](https://document.easyslip.com/th/v2/))

หากนำระบบไปใช้งานจริงและต้องการลดขั้นตอน “อัปโหลดสลิป” แนะนำให้ประเมิน **Omise PromptPay Payment Gateway** เป็นเป้าหมายระยะถัดไป ระบบสร้าง QR เฉพาะรายการและยอดเงิน รับเหตุการณ์ `charge.complete` ผ่าน webhook และตรวจสถานะ charge ซ้ำได้ จึงจับคู่เงินกับคำสั่งซื้อได้ตรงกว่า API ตรวจสลิป แต่มีค่าธรรมเนียม PromptPay 1.65% ต่อรายการ (ไม่รวม VAT) และค่าถอนเงินตามเงื่อนไขของผู้ให้บริการ ([คู่มือ PromptPay](https://docs.omise.co/th/promptpay/thailand?version=2019-05-22), [ราคา Omise ประเทศไทย](https://www.omise.co/th/pricing/thailand))

ไม่ควรให้คำสั่งซื้อเข้าสู่คิวจากผล OCR หรือจากภาพที่ดูเหมือนสลิปเพียงอย่างเดียว ระบบต้องตรวจสถานะธุรกรรมจริง พร้อมตรวจ `transRef`, บัญชีผู้รับ, ยอดเงิน, เวลา และการใช้ซ้ำ ก่อนเปลี่ยนสถานะเป็น `PAID`.

## ขอบเขตและเกณฑ์เปรียบเทียบ

ศึกษาเฉพาะบริการที่มีหน้าเว็บหรือเอกสารจากผู้ให้บริการโดยตรง โดยพิจารณา:

- ค่าเริ่มต้นและโควตาที่เหมาะกับร้านขนาดเล็ก
- วิธีเชื่อมต่อจาก backend และความสามารถตรวจยอด/ผู้รับ/รายการซ้ำ
- รูปแบบการยืนยันแบบ synchronous API หรือ webhook
- ภาระของลูกค้าและพนักงาน
- ความเสี่ยงด้านความพร้อมใช้งาน การผูกติดผู้ให้บริการ และข้อมูลส่วนบุคคล

ราคาและแพ็กเกจอาจเปลี่ยนได้ จึงต้องตรวจหน้าราคาและข้อตกลงอีกครั้งก่อนสมัครหรือเปิดใช้งานจริง

### 1. EasySlip API v2

เอกสารทางการระบุว่า API ใช้ Bearer token และรองรับ IP whitelist, ตรวจผ่าน QR payload, การอัปโหลดรูป, Base64 หรือ URL, ตรวจสลิปซ้ำ และตรวจบัญชีผู้รับ/จำนวนเงินได้ ([หน้าเอกสารหลัก](https://document.easyslip.com/th/)). Endpoint รุ่นล่าสุดคือ `POST https://api.easyslip.com/v2/verify/bank` และมี error ที่ควรจัดการ เช่น `QUOTA_EXCEEDED`, `SLIP_NOT_FOUND` และ `API_SERVER_ERROR` ([ภาพรวม API v2](https://document.easyslip.com/th/v2/)).

แพ็กเกจที่แสดงบนเว็บ ณ วันที่สำรวจมี Tester ฟรี 7 วัน/50 ครั้ง, Start 99 บาท/250 ครั้ง/30 วัน และ Basic 350 บาท/1,000 ครั้ง/30 วัน ([หน้าผลิตภัณฑ์และราคา](https://developer.easyslip.com/product), [หน้าราคาสาธารณะ](https://easyslip.com/api-products/)). ราคาเฉลี่ยหากใช้เต็มโควตาประมาณ 0.396 และ 0.35 บาทต่อครั้งตามลำดับ

แนวทางเชื่อมต่อ:

1. ลูกค้าอัปโหลดสลิป หรือ frontend อ่าน QR payload จากภาพแล้วส่งให้ backend
2. Backend ตรวจชนิดไฟล์/ขนาดและผูก request กับ `payment_attempt_id`
3. Backend เรียก EasySlip ด้วย secret ที่เก็บฝั่ง server เท่านั้น
4. ระบบยืนยัน `success`, `transRef`, จำนวนเงิน, บัญชีผู้รับ และเวลาธุรกรรม พร้อมตรวจว่า `transRef` ไม่เคยถูกใช้
5. เปลี่ยนเป็น `PAID` ภายใน database transaction แล้วจึงปล่อยรายการเข้าคิว
6. หาก API ล่ม/timeout/ผลคลุมเครือ ให้เป็น `PENDING_REVIEW` และส่งให้ Admin ตรวจ ไม่ควรถือว่าจ่ายสำเร็จ

หมายเหตุ: แม้ผู้ให้บริการมี duplicate detection ระบบของร้านควรบังคับ unique constraint ที่ `provider + transRef` ด้วย เพื่อป้องกัน race condition และลดการผูกติดกับผู้ให้บริการรายเดียว

### 2. Slipmate

หน้าเว็บทางการระบุ workflow รับ API key แล้วเชื่อมกับเว็บไซต์/แอป และนำข้อมูลไปตรวจกับธนาคารโดยตรงก่อนคืน Success/Error ([Slipmate](https://www.slipmate.ai/)). แพ็กเกจที่ประกาศคือทดลองใช้ฟรี 100 credits เป็นเวลา 7 วัน, Developer 300 บาท/1,000 credits/30 วัน และ Business 500 บาท/2,500 credits/30 วัน โดยราคายังไม่รวม VAT ([ราคาในหน้าเดียวกัน](https://www.slipmate.ai/#pricing)).

ข้อดีคือทดลองได้ง่ายและต้นทุนเฉลี่ยของ Business อยู่ประมาณ 0.20 บาทต่อการตรวจ แต่ก่อนตัดสินใจควรทดลอง sandbox/บัญชีทดสอบและขอคำตอบเป็นลายลักษณ์อักษรเรื่อง:

- schema ที่ใช้ตรวจบัญชีผู้รับ ยอดเงิน เวลา และรายการซ้ำ
- rate limit, SLA และแนวทางเมื่อธนาคารต้นทางล่ม
- ระยะเวลาเก็บภาพและข้อมูลจากสลิป การลบข้อมูล และผู้ประมวลผลช่วงต่อ
- webhook signature (หากมี webhook) และการ rotate API key

หากคำตอบเหล่านี้ไม่ชัด ให้เลือก EasySlip ซึ่งเอกสารสาธารณะระบุความสามารถเชิงเทคนิคมากกว่า

### 3. SlipOK API

SlipOK ระบุว่าสามารถส่งรูปสลิปหรือ code ที่อ่านจาก QR ไปตรวจ และมีบริการ API/LINE OA Webhook ([หน้า API](https://slipok.com/api/), [หน้าแรก SlipOK](https://slipok.com/)). หน้าราคาหลัก ณ วันที่สำรวจแสดง Basic ฟรี 100 ครั้ง/เดือน, Start 350 บาท/500 ครั้ง, SME 600 บาท/1,000 ครั้ง และ Enterprise 1,000 บาท/2,000 ครั้ง ([ราคา SlipOK](https://slipok.com/our-service/)). หน้า FAQ ระบุค่าใช้เกินโควตา 1.0/0.7/0.6/0.5 บาทต่อรายการตามแพ็กเกจ และแพ็กเกจรายเดือนไม่ยกโควตาข้ามเดือน ([FAQ API](https://dev.slipok.com/api/)). เนื่องจากบางหน้าบนเว็บไซต์แสดงตัวเลขไม่ตรงกัน ต้องยืนยันราคาและเงื่อนไขกับฝ่ายขายก่อนสมัคร

ความเสี่ยงเฉพาะที่ต้องประเมินคือผู้ให้บริการระบุว่าบันทึกข้อมูลร้านและประวัติการตรวจตั้งแต่วันสมัคร “ตลอดไป” และการยกเลิกต้องแจ้งล่วงหน้าอย่างน้อย 30 วัน ([FAQ API](https://dev.slipok.com/api/)). ภาพสลิปมีชื่อ เลขบัญชีบางส่วน ยอด และเวลา จึงควรอ่าน privacy policy/สัญญาประมวลผลข้อมูล กำหนดฐานการประมวลผล แจ้งลูกค้า และหลีกเลี่ยงเก็บภาพต้นฉบับในระบบของร้านนานเกินจำเป็น

### 4. Omise PromptPay Payment Gateway

ต่างจากสามรายแรก Omise เป็นช่องทางรับชำระ ไม่ใช่แค่ตรวจหลักฐาน ลูกค้าได้รับ QR ที่กำหนดยอดและใช้ชำระได้ครั้งเดียว เมื่อสำเร็จร้านรับ `charge.complete` webhook และเอกสารแนะนำให้เรียกตรวจ charge ซ้ำเพื่อความแม่นยำ ([PromptPay integration](https://docs.omise.co/th/promptpay/thailand?version=2019-05-22)).

ราคา PromptPay ที่ประกาศคือ 1.65% ต่อรายการ ไม่รวม VAT ([ราคา Omise](https://www.omise.co/th/pricing/thailand)). ผู้ให้บริการระบุว่าไม่มีค่าติดตั้ง ค่ารายเดือน หรือยอดขั้นต่ำ แต่มีค่าธรรมเนียมเมื่อโอนยอดออกไปบัญชีธนาคาร ([คำอธิบายค่าบริการ](https://docs.omise.co/th/how-much-does-omise-cost/thailand)). ต้องตรวจอัตราถอนเงินล่าสุดใน dashboard/สัญญา เพราะหน้าเว็บทางการต่างหน้ามีตัวเลข 20 และ 30 บาทในช่วงที่สำรวจ

Gateway เหมาะกว่า slip API เมื่อ:

- ต้องการให้การจ่ายก่อนเป็นเงื่อนไขอัตโนมัติและลดงาน Admin จริง
- ต้องการ QR เฉพาะ order และปิดช่องโหว่ยอด/บัญชี/สลิปซ้ำตั้งแต่ต้นทาง
- ยอมรับค่าธรรมเนียมและรอบนำส่งเงินได้
- ร้านผ่านขั้นตอน onboarding/KYC และมี backend ที่รับ HTTPS webhook ได้

## Requirement ที่เสนอให้บันทึกในระบบ

### Functional requirements

- `PAY-01` ระบบต้องสร้าง `payment_attempt` ต่อคำสั่งซื้อและกำหนดยอดที่คาดหวังเป็นค่าคงที่หลังยืนยันรายการ
- `PAY-02` รุ่นแรกต้องรับสลิปจากลูกค้าและส่งตรวจผ่าน provider adapter โดย API key ต้องอยู่ฝั่ง backend เท่านั้น
- `PAY-03` ระบบจะยืนยันการชำระเมื่อผู้ให้บริการยืนยันธุรกรรมจริง และ `amount`, `receiver`, `transRef` และเวลาตรงตามเงื่อนไขทั้งหมด
- `PAY-04` ระบบต้องปฏิเสธ `transRef` ที่เคยใช้สำเร็จแล้ว แม้ผลจาก provider ไม่ระบุว่าเป็นรายการซ้ำ
- `PAY-05` การตรวจล้มเหลวจาก timeout, provider outage, quota หรือผลไม่ครบ ต้องเป็น `PENDING_REVIEW` ไม่ใช่ `PAID` หรือ `FAILED` อัตโนมัติ
- `PAY-06` Admin ต้องดูหลักฐานและยืนยัน/ปฏิเสธด้วยมือได้ โดยบันทึกผู้ดำเนินการ เวลา เหตุผล และข้อมูลก่อน–หลัง
- `PAY-07` คำสั่งซื้อล่วงหน้า/กลับบ้านจะเข้าคิวได้เมื่อสถานะเป็น `PAID` เท่านั้น
- `PAY-08` endpoint รับ webhook ในอนาคตต้องตรวจ signature (ถ้าผู้ให้บริการรองรับ), ทำ idempotency และเรียก provider API ตรวจสถานะซ้ำก่อนยืนยัน
- `PAY-09` ระบบต้องมี provider-neutral adapter เพื่อเปลี่ยนจาก EasySlip ไป gateway หรือผู้ตรวจสลิปรายอื่นโดยไม่แก้ business logic ของ order

### Suggested states

`CREATED -> AWAITING_PROOF -> VERIFYING -> PAID`

เส้นทางผิดปกติ:

- `VERIFYING -> PENDING_REVIEW -> PAID | REJECTED`
- `AWAITING_PROOF | VERIFYING -> EXPIRED`
- `PAID -> REFUND_PENDING -> REFUNDED` (เมื่อรองรับคืนเงิน)

ห้ามให้ผู้ใช้ทั่วไปหรือ Admin แก้ `PAID` โดยตรงโดยไม่มี audit event

## ความเสี่ยงและมาตรการควบคุม

1. **ผู้ให้บริการล่มหรือธนาคารต้นทางไม่ตอบ:** ใช้ timeout จำกัด, retry แบบมี backoff เฉพาะกรณีปลอดภัย และเปิด manual review; ห้ามสร้าง payment ใหม่ทุก retry
2. **สลิปเดียวใช้หลายออเดอร์:** unique index ที่ `provider + transRef` และทำการเปลี่ยน order/payment ใน transaction เดียว
3. **ยอดเดียวกันจากหลายลูกค้า:** ห้ามจับคู่จากยอดอย่างเดียว ต้องใช้ reference/ข้อมูลธุรกรรมและบัญชีผู้รับ
4. **API key รั่ว:** เก็บใน secret manager/environment ฝั่ง server, ไม่ส่งลง browser/LIFF, จำกัด IP หากรองรับ และหมุน key ได้
5. **ข้อมูลส่วนบุคคลบนสลิป:** ขอเฉพาะข้อมูลจำเป็น กำหนด retention สั้น ลบภาพหลังพ้นช่วงตรวจสอบ จำกัดสิทธิ์ Admin และบันทึกการเข้าถึง
6. **ราคา/ข้อกำหนดเปลี่ยน:** ทำ provider adapter และกำหนด config สำหรับ quota/timeout เพื่อสลับผู้ให้บริการได้
7. **ผลตรวจ false positive/ข้อมูลตอบกลับไม่ครบ:** ตรวจหลายฟิลด์เสมอและส่ง manual review แทนการอนุมัติแบบผ่อนปรน

## แผนทดลองก่อนเลือกจริง

1. สมัคร trial ของ EasySlip และ Slipmate โดยไม่ใส่ข้อมูลเงินจริงเกินจำเป็น
2. สร้างชุดทดสอบอย่างน้อย: สลิปจริงถูกยอด, ผิดยอด, ผิดผู้รับ, ซ้ำ, เก่า, ภาพแตก, ไม่มี QR, รูปแก้ไข และ provider timeout
3. วัด response time, error schema, duplicate behavior และ quota accounting อย่างน้อย 50–100 ครั้ง
4. ขอเอกสาร privacy/retention, SLA, rate limit และเงื่อนไขยกเลิกจากผู้ให้บริการที่ผ่านการทดสอบ
5. เลือก EasySlip หากผลใกล้เคียงกันเพราะเอกสารและค่าเริ่มต้นเหมาะกับ PoC; เลือก Slipmate หากผลทดสอบดีกว่าและยืนยันข้อกำหนดความปลอดภัยได้
6. เมื่อเปิดใช้งานจริงและมีจำนวนคำสั่งซื้อสม่ำเสมอ ให้เปรียบเทียบต้นทุนรวมและขั้นตอนผู้ใช้กับ Omise PromptPay อีกครั้ง
