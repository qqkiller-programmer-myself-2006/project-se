# ข้อกำหนดระบบบริหารจัดการร้านอาหาร

## 1 วัตถุประสงค์ของเอกสาร

เอกสารนี้แปลงเนื้อหาบทที่ 1 ถึงบทที่ 3 ของรายงานโครงงานเรื่องระบบบริหารจัดการร้านอาหารแบบครบวงจรผ่านเว็บไซต์ร่วมกับ LINE Official Account ให้เป็นข้อกำหนดที่ใช้วางแผน ออกแบบ พัฒนา และทดสอบระบบได้

แหล่งข้อมูลตั้งต้นคือ `docs/Real_Report.docx` ข้อกำหนดที่เอกสารต้นทางยังระบุไม่เพียงพอจะถูกจัดไว้ในหัวข้อ “ประเด็นที่ต้องยืนยัน” และยังไม่ถือเป็นข้อตกลงสำหรับการพัฒนา

## 2 เป้าหมายของระบบ

ระบบต้องช่วยร้านอาหารขนาดกลางหรือขนาดเล็กที่มีบุคลากรจำกัดบริหารการจองโต๊ะ คำสั่งซื้อ คิวอาหารและเครื่องดื่ม วัตถุดิบ การชำระเงิน รายรับรายจ่าย คะแนนสะสม และข้อมูลเพื่อการตัดสินใจผ่านเว็บแอปพลิเคชันที่เชื่อมต่อกับ LINE Official Account

ผลลัพธ์ที่ต้องการคือ

1. ลดการจดข้อมูลและการประสานงานด้วยวาจา
2. ลดคำสั่งซื้อผิดพลาดและการจองโต๊ะซ้ำ
3. ให้ลูกค้าตรวจสอบสถานะร้าน จองโต๊ะ สั่งซื้อ ชำระเงิน และติดตามงานได้จากช่องทางออนไลน์
4. ให้พนักงานจัดการคิวอาหารและเครื่องดื่มตามลำดับได้อย่างชัดเจน
5. ให้เจ้าของร้านเห็นข้อมูลการดำเนินงานและผลประกอบการที่เป็นปัจจุบัน
6. เก็บข้อมูลเวลาปฏิบัติงานสำหรับพยากรณ์เวลารอรับบริการ

## 3 ขอบเขตระบบ

### 3.1 อยู่ในขอบเขต

- เว็บไซต์แบบ Responsive สำหรับลูกค้าและบุคลากรของร้าน
- การเชื่อมบัญชีลูกค้ากับ LINE Official Account
- การแจ้งเตือนผ่าน LINE Messaging API
- การจัดการสมาชิกและสิทธิ์ตามบทบาท
- สถานะร้านและสถานะโต๊ะแบบปัจจุบัน
- การจองโต๊ะ
- การสั่งอาหารและเครื่องดื่มล่วงหน้า การสั่งกลับบ้าน และคำสั่งซื้อของลูกค้า Walk-in
- การชำระเงินก่อนเริ่มดำเนินการ
- คิวอาหารและเครื่องดื่มแบบ FIFO
- การจัดการเมนู สูตรวัตถุดิบ และสต๊อก
- คะแนนสะสมสำหรับเครื่องดื่มและการแลกของรางวัล
- รายรับ รายจ่าย รายงาน และ Dashboard
- การเก็บข้อมูลและแสดงผลพยากรณ์เวลารอรับบริการ

### 3.2 ยังไม่อยู่ในขอบเขตจนกว่าจะยืนยัน

- ระบบส่งอาหารและการติดตามพนักงานจัดส่ง
- การจัดซื้อวัตถุดิบจากซัพพลายเออร์
- เงินเดือน ตารางกะ และการลงเวลาพนักงาน
- ระบบบัญชีและภาษีเต็มรูปแบบ
- การบริหารหลายสาขา
- การพัฒนาโมเดลภาษาขนาดใหญ่ขึ้นเอง

## 4 ผู้มีส่วนเกี่ยวข้องและบทบาท

| บทบาท | หน้าที่หลัก |
|---|---|
| ลูกค้า | ดูข้อมูลร้าน จองโต๊ะ สั่งซื้อ ชำระเงิน ติดตามสถานะ และใช้คะแนนสะสม |
| แม่ครัว | รับและดำเนินการคิวอาหาร บันทึกเวลา และเปลี่ยนสถานะ |
| ผู้ดูแลเครื่องดื่ม | รับและดำเนินการคิวเครื่องดื่ม บันทึกเวลา และออก QR Code คะแนน Walk-in |
| ผู้ดูแลระบบ | จัดการข้อมูลหลัก การจอง คำสั่งซื้อ วัตถุดิบ การเงิน และตรวจสอบการชำระเงิน |
| เจ้าของร้าน | ดู Dashboard รายงาน สถานะร้าน และผลพยากรณ์ |
| LINE Platform | ยืนยันตัวตนหรือเชื่อมบัญชี และรับส่งข้อความแจ้งเตือน |
| ผู้ให้บริการชำระเงิน | รับและยืนยันผลการชำระเงินเมื่อกำหนดผู้ให้บริการแล้ว |
| บริการพยากรณ์ | รับข้อมูลคุณลักษณะและส่งค่าประมาณเวลารอเมื่อกำหนดวิธีใช้งานแล้ว |

## 5 Functional Requirements

### 5.1 บัญชีผู้ใช้และสิทธิ์

- **FR-AUTH-001** ระบบต้องให้ลูกค้าสมัครสมาชิกและเข้าสู่ระบบผ่านเว็บไซต์ได้
  - เกณฑ์ยอมรับ: เมื่อกรอกข้อมูลที่จำเป็นครบและไม่ซ้ำ ระบบสร้างบัญชีและให้เข้าสู่ระบบได้
- **FR-AUTH-002** ระบบต้องให้ลูกค้าเชื่อมบัญชีกับ LINE Official Account ได้
  - เกณฑ์ยอมรับ: ระบบบันทึกความสัมพันธ์ระหว่างสมาชิกหนึ่งรายกับ LINE user ID และป้องกันการเชื่อมซ้ำที่ขัดแย้งกัน
- **FR-AUTH-003** ระบบต้องจำกัดการเข้าถึงตามบทบาทลูกค้า แม่ครัว ผู้ดูแลเครื่องดื่ม ผู้ดูแลระบบ และเจ้าของร้าน
  - เกณฑ์ยอมรับ: ผู้ใช้ที่ไม่มีสิทธิ์ไม่สามารถเปิดหน้าหรือเรียกใช้คำสั่งของบทบาทอื่นได้
- **FR-AUTH-004** ผู้ดูแลระบบต้องค้นหา ดู แก้ไขสถานะ และจัดการข้อมูลสมาชิกได้
  - เกณฑ์ยอมรับ: การเปลี่ยนแปลงถูกบันทึกและมีผลกับการใช้งานครั้งถัดไป

### 5.2 สถานะร้านและโต๊ะ

- **FR-SHOP-001** ลูกค้าต้องดูสถานะเปิดหรือปิดของร้าน จำนวนโต๊ะว่าง และจำนวนลูกค้าที่กำลังใช้บริการได้
  - เกณฑ์ยอมรับ: หน้าสถานะใช้ข้อมูลปัจจุบันจากระบบและแสดงเวลาอัปเดตล่าสุด
- **FR-TABLE-001** ผู้ดูแลระบบต้องเพิ่ม แก้ไข และเปลี่ยนสถานะโต๊ะพร้อมจำนวนที่นั่งได้
  - เกณฑ์ยอมรับ: หมายเลขโต๊ะไม่ซ้ำและจำนวนที่นั่งต้องมากกว่าศูนย์
- **FR-TABLE-002** ระบบต้องไม่เสนอหรืออนุญาตให้จองโต๊ะที่ไม่ว่างในช่วงเวลาที่เลือก
  - เกณฑ์ยอมรับ: คำขอจองพร้อมกันสำหรับโต๊ะและช่วงเวลาเดียวกันสำเร็จได้เพียงรายการเดียว
- **FR-TABLE-003** ระบบต้องแนะนำโต๊ะตามจำนวนลูกค้าและสถานะว่างได้
  - เกณฑ์ยอมรับ: โต๊ะที่แนะนำมีที่นั่งเพียงพอและว่างในช่วงเวลาที่จอง

### 5.3 การจองโต๊ะ

- **FR-RES-001** ลูกค้าต้องสร้างการจองโดยระบุวัน เวลา จำนวนผู้ใช้บริการ และโต๊ะที่เลือกหรือโต๊ะที่ระบบแนะนำได้
  - เกณฑ์ยอมรับ: ระบบตรวจความพร้อมก่อนสร้างรายการและส่งเลขอ้างอิงการจองให้ลูกค้า
- **FR-RES-002** ลูกค้าต้องตรวจสอบสถานะการจองของตนเองได้
  - เกณฑ์ยอมรับ: ลูกค้าเห็นเฉพาะรายการของตนพร้อมวัน เวลา โต๊ะ และสถานะล่าสุด
- **FR-RES-003** ผู้ดูแลระบบต้องค้นหา ดู และเปลี่ยนสถานะการจองได้
  - เกณฑ์ยอมรับ: สถานะที่เปลี่ยนถูกบันทึกและสะท้อนในหน้าของลูกค้า
- **FR-RES-004** ระบบต้องแจ้งผลยืนยันและการเปลี่ยนสถานะการจองผ่าน LINE สำหรับบัญชีที่เชื่อมต่อแล้ว
  - เกณฑ์ยอมรับ: ระบบสร้างประวัติการส่งและรองรับการส่งใหม่เมื่อบริการ LINE ขัดข้อง

### 5.4 เมนูและคำสั่งซื้อ

- **FR-MENU-001** ลูกค้าต้องดูรายการอาหารและเครื่องดื่ม แยกหมวดหมู่ พร้อมชื่อ รายละเอียด รูปภาพ ราคา และสถานะพร้อมขายได้
  - เกณฑ์ยอมรับ: รายการที่งดขายไม่สามารถเพิ่มลงคำสั่งซื้อใหม่ได้
- **FR-MENU-002** ผู้ดูแลระบบต้องเพิ่ม แก้ไข และเปลี่ยนสถานะเมนูได้
  - เกณฑ์ยอมรับ: ชื่อ ราคา หมวดหมู่ และสถานะผ่านการตรวจสอบก่อนบันทึก
- **FR-ORD-001** ลูกค้าต้องสร้างคำสั่งซื้อแบบรับประทานที่ร้านล่วงหน้าหรือแบบกลับบ้านได้
  - เกณฑ์ยอมรับ: คำสั่งซื้อมีประเภทการรับบริการ รายการ จำนวน ราคา และยอดรวมที่คำนวณจากข้อมูลขณะยืนยัน
- **FR-ORD-002** ระบบต้องแยกรายการอาหารไปคิวครัวและรายการเครื่องดื่มไปคิวเครื่องดื่ม
  - เกณฑ์ยอมรับ: รายการทุกชิ้นปรากฏในคิวของฝ่ายที่รับผิดชอบเพียงฝ่ายเดียว
- **FR-ORD-003** ลูกค้าต้องตรวจสอบสถานะคำสั่งซื้อและสถานะรายรายการได้
  - เกณฑ์ยอมรับ: สถานะรวมสอดคล้องกับสถานะของรายการย่อยและแสดงเวลาปรับปรุงล่าสุด
- **FR-ORD-004** ผู้ดูแลระบบต้องค้นหา ดู และจัดการคำสั่งซื้อได้ตามสิทธิ์
  - เกณฑ์ยอมรับ: การแก้ไขหลังชำระเงินมีประวัติผู้ดำเนินการ เวลา เหตุผล และค่าก่อนกับหลัง

### 5.5 การชำระเงิน

- **FR-PAY-001** ระบบต้องคำนวณยอดชำระจากรายการและจำนวนในคำสั่งซื้อ
  - เกณฑ์ยอมรับ: ยอดรวมถูกตรึงไว้กับคำสั่งซื้อเมื่อส่งคำขอชำระเงิน
- **FR-PAY-002** ลูกค้าต้องชำระเงินเต็มจำนวนก่อนคำสั่งซื้อเข้าสู่คิวดำเนินการ
  - เกณฑ์ยอมรับ: ระบบไม่สร้างงานในคิวจนกว่าจะได้รับผลยืนยันการชำระเงินสำเร็จ
- **FR-PAY-003** ระบบต้องบันทึกจำนวนเงิน วิธีชำระ เวลา สถานะ และเลขอ้างอิงการชำระเงิน
  - เกณฑ์ยอมรับ: เหตุการณ์ยืนยันซ้ำด้วยเลขอ้างอิงเดียวกันไม่สร้างการชำระเงินซ้ำ
- **FR-PAY-004** ผู้ดูแลระบบต้องตรวจสอบรายการชำระเงินและสถานะที่เกี่ยวข้องได้
  - เกณฑ์ยอมรับ: ค้นหาได้อย่างน้อยด้วยเลขคำสั่งซื้อ วันที่ และสถานะ

### 5.6 คิวอาหารและเครื่องดื่ม

- **FR-QUEUE-001** ระบบต้องจัดคิวที่พร้อมดำเนินการตามเวลาที่ชำระเงินสำเร็จแบบ First In First Out แยกระหว่างอาหารและเครื่องดื่ม
  - เกณฑ์ยอมรับ: หากไม่มีเงื่อนไขยกเว้น รายการที่พร้อมก่อนต้องอยู่ก่อนรายการที่พร้อมภายหลัง
- **FR-QUEUE-002** แม่ครัวและผู้ดูแลเครื่องดื่มต้องเห็นเฉพาะคิวของฝ่ายตนแบบปัจจุบัน
  - เกณฑ์ยอมรับ: รายการใหม่หรือสถานะใหม่ปรากฏโดยไม่ต้องออกจากระบบ
- **FR-QUEUE-003** ผู้ปฏิบัติงานต้องเปลี่ยนสถานะรายการตามลำดับ `รอ -> กำลังทำ -> เสร็จสิ้น` ได้
  - เกณฑ์ยอมรับ: ระบบป้องกันการข้ามหรือย้อนสถานะ ยกเว้นผู้มีสิทธิ์แก้ไขพร้อมระบุเหตุผล
- **FR-QUEUE-004** ระบบต้องบันทึกเวลาเข้าคิว เวลาเริ่ม และเวลาเสร็จของแต่ละรายการ
  - เกณฑ์ยอมรับ: เวลาเริ่มไม่ก่อนเวลาเข้าคิว และเวลาเสร็จไม่ก่อนเวลาเริ่ม
- **FR-QUEUE-005** ระบบต้องแจ้งลูกค้าเมื่อสถานะคำสั่งซื้อเปลี่ยนถึงจุดที่กำหนด
  - เกณฑ์ยอมรับ: การแจ้งเตือนอ้างอิงคำสั่งซื้อและสถานะที่ถูกต้อง พร้อมบันทึกผลการส่ง

### 5.7 วัตถุดิบและสต๊อก

- **FR-INV-001** ผู้ดูแลระบบต้องเพิ่ม แก้ไข และดูจำนวนคงเหลือของวัตถุดิบได้
  - เกณฑ์ยอมรับ: วัตถุดิบแต่ละรายการมีชื่อ หน่วยนับ และจำนวนคงเหลือ
- **FR-INV-002** ผู้ดูแลระบบต้องกำหนดสูตรเชื่อมเมนูกับวัตถุดิบและปริมาณที่ใช้ได้
  - เกณฑ์ยอมรับ: เมนูหนึ่งรายการเชื่อมได้หลายวัตถุดิบและวัตถุดิบหนึ่งรายการใช้ได้กับหลายเมนู
- **FR-INV-003** ระบบต้องตัดสต๊อกตามสูตรเมื่อคำสั่งซื้อผ่านเงื่อนไขที่กำหนด
  - เกณฑ์ยอมรับ: การตัดแต่ละครั้งอ้างอิงคำสั่งซื้อและไม่ตัดซ้ำเมื่อรับเหตุการณ์เดิมซ้ำ
- **FR-INV-004** ระบบต้องป้องกันหรือแจ้งเตือนการขายเมนูเมื่อวัตถุดิบไม่เพียงพอตามนโยบายที่ยืนยันแล้ว
  - เกณฑ์ยอมรับ: ผลตรวจใช้ยอดคงเหลือและสูตรล่าสุดก่อนยืนยันคำสั่งซื้อ

### 5.8 คะแนนสะสมและของรางวัล

- **FR-LOY-001** ระบบต้องเพิ่มคะแนนจากการซื้อเครื่องดื่มตามกติกาที่กำหนด
  - เกณฑ์ยอมรับ: ธุรกรรมคะแนนอ้างอิงคำสั่งซื้อหรือเหตุการณ์ Walk-in และไม่เพิ่มซ้ำ
- **FR-LOY-002** ผู้ดูแลเครื่องดื่มต้องสร้าง QR Code สำหรับรับคะแนนของลูกค้า Walk-in ได้
  - เกณฑ์ยอมรับ: QR Code มีอายุและใช้รับคะแนนได้ตามจำนวนครั้งที่กำหนด
- **FR-LOY-003** ลูกค้าต้องดูยอดคงเหลือและประวัติรับหรือใช้คะแนนได้
  - เกณฑ์ยอมรับ: ยอดคงเหลือเท่ากับผลรวมธุรกรรมคะแนนที่มีผล
- **FR-LOY-004** ลูกค้าต้องแลกคะแนนเป็นของรางวัลที่ยังพร้อมแลกได้
  - เกณฑ์ยอมรับ: ระบบตรวจคะแนนก่อนยืนยัน หักคะแนนครั้งเดียว และสร้างหลักฐานการแลก

### 5.9 รายรับ รายจ่าย และ Dashboard

- **FR-FIN-001** ระบบต้องสร้างรายการรายรับจากการชำระเงินที่สำเร็จ
  - เกณฑ์ยอมรับ: รายรับอ้างอิงการชำระเงินและไม่บันทึกซ้ำ
- **FR-FIN-002** ผู้ดูแลระบบต้องบันทึก แก้ไข และจัดหมวดหมู่รายจ่ายได้
  - เกณฑ์ยอมรับ: รายจ่ายมีจำนวน วันที่ หมวดหมู่ รายละเอียด และผู้บันทึก
- **FR-DASH-001** เจ้าของร้านต้องดูยอดขายรายวัน รายเดือน และรายปีได้
  - เกณฑ์ยอมรับ: ผู้ใช้เลือกช่วงเวลาได้และยอดรวมสอดคล้องกับรายการชำระเงินสำเร็จ
- **FR-DASH-002** เจ้าของร้านต้องดูรายรับ รายจ่าย และกำไรเบื้องต้นได้
  - เกณฑ์ยอมรับ: หน้าจอแสดงสูตรที่ใช้และช่วงเวลาของข้อมูล
- **FR-DASH-003** เจ้าของร้านต้องดูเมนูขายดีและช่วงเวลาที่มีลูกค้าใช้บริการหนาแน่นได้
  - เกณฑ์ยอมรับ: ระบบระบุเกณฑ์จัดอันดับ หน่วยนับ และช่วงเวลาที่นำมาคำนวณ
- **FR-DASH-004** เจ้าของร้านต้องดูสถานะร้าน โต๊ะ และคิวที่กำลังดำเนินการได้
  - เกณฑ์ยอมรับ: หน้าจอแสดงเวลาอัปเดตล่าสุดและแยกสถานะตามประเภทงาน

### 5.10 การพยากรณ์เวลารอ

- **FR-ML-001** ระบบต้องจัดเก็บข้อมูลที่จำเป็นต่อการพยากรณ์ ได้แก่ เวลาเข้าคิว เวลาเริ่ม เวลาเสร็จ ประเภทหรือเมนู จำนวนรายการรอ และช่วงเวลาของวัน
  - เกณฑ์ยอมรับ: ข้อมูลหนึ่งระเบียนเชื่อมย้อนกลับถึงรายการสั่งซื้อได้และมีเวลาครบเมื่อรายการเสร็จ
- **FR-ML-002** ระบบต้องขอค่าพยากรณ์เวลารอจากโมเดลหรือบริการที่กำหนด
  - เกณฑ์ยอมรับ: ระบบส่งข้อมูลตาม schema ที่ตกลงและตรวจสอบรูปแบบผลลัพธ์ก่อนแสดงผล
- **FR-ML-003** ลูกค้าและเจ้าของร้านต้องเห็นค่าพยากรณ์พร้อมเวลาที่คำนวณ
  - เกณฑ์ยอมรับ: ระบบระบุว่าเป็นค่าประมาณ ไม่แสดงค่าที่หมดอายุ และมีวิธีสำรองเมื่อบริการไม่พร้อม
- **FR-ML-004** ระบบต้องเก็บค่าพยากรณ์และเวลาจริงเพื่อประเมินความคลาดเคลื่อน
  - เกณฑ์ยอมรับ: สามารถคำนวณความคลาดเคลื่อนของรายการที่ดำเนินการเสร็จแล้วได้

## 6 Business Rules

- **BR-001** คำสั่งซื้อเข้าสู่คิวได้เมื่อชำระเงินเต็มจำนวนสำเร็จแล้ว
- **BR-002** คิวอาหารและคิวเครื่องดื่มแยกจากกัน
- **BR-003** ลำดับพื้นฐานของคิวคือ FIFO โดยใช้เวลาที่รายการพร้อมดำเนินการ
- **BR-004** รายการอาหารดำเนินการโดยแม่ครัว และรายการเครื่องดื่มดำเนินการโดยผู้ดูแลเครื่องดื่ม
- **BR-005** การจองหนึ่งรายการต้องอ้างอิงลูกค้าและโต๊ะหนึ่งโต๊ะ
- **BR-006** โต๊ะหนึ่งโต๊ะต้องไม่มีการจองที่ทับซ้อนกันตามช่วงเวลาที่ระบบกำหนด
- **BR-007** คำสั่งซื้อหนึ่งรายการมีรายการย่อยอย่างน้อยหนึ่งรายการ
- **BR-008** รายการย่อยแต่ละรายการอ้างอิงเมนูหนึ่งรายการและมีจำนวนมากกว่าศูนย์
- **BR-009** การตัดสต๊อกและธุรกรรมคะแนนต้องทำแบบ idempotent เพื่อป้องกันผลซ้ำ
- **BR-010** คะแนนสะสมตามเอกสารต้นทางใช้กับเครื่องดื่มเท่านั้น จนกว่าจะมีการเปลี่ยนนโยบาย
- **BR-011** กำไรที่แสดงเป็นกำไรเบื้องต้นตามสูตร `รายรับ - รายจ่ายที่บันทึกในระบบ` ไม่ใช่งบกำไรขาดทุนทางบัญชี
- **BR-012** ค่าพยากรณ์เวลารอเป็นค่าประมาณและต้องไม่แทนเวลารับประกันบริการ

## 7 Data Requirements

### 7.1 เอนทิตีหลัก

| เอนทิตี | ข้อมูลขั้นต่ำ | ความสัมพันธ์สำคัญ |
|---|---|---|
| Customer | รหัสลูกค้า LINE user ID ชื่อ โทรศัพท์ อีเมล คะแนนแสดงผล | มีหลายการจอง คำสั่งซื้อ และธุรกรรมคะแนน |
| User Account | รหัสผู้ใช้ ข้อมูลเข้าสู่ระบบ บทบาท สถานะ | อ้างอิงบุคคลหรือพนักงานตามแบบข้อมูลที่เลือก |
| Restaurant Table | รหัสโต๊ะ หมายเลข จำนวนที่นั่ง สถานะ | มีหลายการจองและคำสั่งซื้อ |
| Reservation | รหัส ลูกค้า โต๊ะ เวลา จำนวนคน สถานะ | อ้างอิง Customer และ Restaurant Table |
| Menu Item | รหัส ชื่อ รายละเอียด หมวดหมู่ ราคา รูป สถานะ | มีหลาย Order Item และหลาย Menu Ingredient |
| Ingredient | รหัส ชื่อ หน่วย จำนวนคงเหลือ | มีหลาย Menu Ingredient และ Stock Transaction |
| Menu Ingredient | เมนู วัตถุดิบ ปริมาณต่อหน่วย | ตารางเชื่อม Menu Item กับ Ingredient |
| Order | รหัส ลูกค้า โต๊ะหรือจุดรับ ประเภท เวลา สถานะ ยอดรวม | มีหลาย Order Item และ Payment |
| Order Item | รหัส Order เมนู จำนวน ราคา สถานะคิว เวลาเข้าคิว เริ่ม เสร็จ | อ้างอิง Order และ Menu Item |
| Payment | รหัส Order จำนวน วิธี สถานะ เวลา เลขอ้างอิง | อ้างอิง Order |
| Stock Transaction | รหัส วัตถุดิบ จำนวน ทิศทาง เหตุผล Order เวลา | ใช้คำนวณและตรวจสอบสต๊อก |
| Loyalty Transaction | รหัส ลูกค้า คะแนน ทิศทาง แหล่งที่มา เวลา | ใช้คำนวณยอดคะแนน |
| Reward | รหัส ชื่อ คะแนนที่ใช้ สถานะ จำนวนคงเหลือ | มีหลายรายการแลก |
| Expense | รหัส จำนวน วันที่ หมวดหมู่ รายละเอียด ผู้บันทึก | ใช้คำนวณกำไรเบื้องต้น |
| Notification | ผู้รับ ช่องทาง เหตุการณ์ เนื้อหา สถานะ เวลา | อ้างอิงการจองหรือคำสั่งซื้อเมื่อเกี่ยวข้อง |
| Wait Prediction | Order หรือ Order Item คุณลักษณะ ค่าพยากรณ์ เวลาจริง รุ่นโมเดล เวลา | ใช้ประเมินความคลาดเคลื่อน |

### 7.2 ความถูกต้องและการตรวจสอบย้อนหลัง

- ข้อมูลการเงิน การชำระเงิน สต๊อก คะแนน และการเปลี่ยนสถานะสำคัญต้องมีเวลาและผู้ดำเนินการหรือแหล่งเหตุการณ์
- ประวัติธุรกรรมต้องคงอยู่แม้ข้อมูลหลักถูกปิดใช้งาน
- เวลาทั้งระบบต้องใช้เขตเวลาเดียวกันและจัดเก็บในรูปแบบที่แปลงเขตเวลาได้
- ราคาที่ใช้ในคำสั่งซื้อ ต้องเก็บเป็น snapshot เพื่อไม่เปลี่ยนตามราคาปัจจุบันของเมนู
- การเปลี่ยนข้อมูลที่มีผลต่อยอดเงิน สต๊อก หรือคะแนนต้องตรวจสอบย้อนหลังได้

## 8 Non-functional Requirements

ค่าตัวเลขที่เอกสารต้นทางไม่ได้กำหนดจะระบุเป็นเป้าหมายเริ่มต้นและต้องยืนยันก่อนใช้เป็นเกณฑ์ส่งมอบ

- **NFR-SEC-001** รหัสผ่านต้องจัดเก็บด้วย password hashing ที่เหมาะสม ห้ามเก็บเป็นข้อความปกติ
- **NFR-SEC-002** การรับส่งข้อมูลที่มีข้อมูลส่วนบุคคลหรือข้อมูลการชำระเงินต้องใช้ HTTPS
- **NFR-SEC-003** API ต้องตรวจสอบตัวตนและสิทธิ์ฝั่งเซิร์ฟเวอร์ทุกครั้ง
- **NFR-SEC-004** Webhook จาก LINE และผู้ให้บริการชำระเงินต้องตรวจลายเซ็นหรือกลไกยืนยันแหล่งที่มา
- **NFR-SEC-005** ข้อมูลส่วนบุคคลต้องถูกเก็บและแสดงเท่าที่จำเป็นตามวัตถุประสงค์
- **NFR-PERF-001** เป้าหมายเริ่มต้น: คำขอทั่วไป 95% ต้องตอบภายใน 2 วินาทีภายใต้ภาระงานที่ตกลง
- **NFR-PERF-002** เป้าหมายเริ่มต้น: การเปลี่ยนแปลงคิวต้องปรากฏแก่พนักงานภายใน 5 วินาที
- **NFR-REL-001** การรับ webhook ซ้ำต้องไม่ทำให้เกิดการชำระเงิน ตัดสต๊อก เพิ่มคะแนน หรือสร้างคิวซ้ำ
- **NFR-REL-002** ระบบต้องมีวิธี retry และบันทึกข้อผิดพลาดเมื่อ LINE บริการชำระเงิน หรือบริการพยากรณ์ไม่พร้อม
- **NFR-REL-003** ฐานข้อมูลต้องสำรองและกู้คืนได้ตาม RPO และ RTO ที่เจ้าของระบบยืนยัน
- **NFR-USE-001** หน้าจอต้องรองรับคอมพิวเตอร์ สมาร์ตโฟน และแท็บเล็ต
- **NFR-USE-002** หน้าคิวต้องอ่านและเปลี่ยนสถานะได้รวดเร็วในช่วงงานเร่งด่วน โดยปุ่มหลักต้องแยกสถานะชัดเจน
- **NFR-OBS-001** ระบบต้องบันทึก error log และ audit log โดยไม่บันทึกรหัสผ่าน token หรือข้อมูลชำระเงินที่เป็นความลับ
- **NFR-MNT-001** Frontend Backend งานประมวลผลข้อมูล และฐานข้อมูลต้องแยกความรับผิดชอบและกำหนด interface ที่ชัดเจน
- **NFR-COMP-001** การจัดการข้อมูลลูกค้าต้องรองรับการแจ้งวัตถุประสงค์ การแก้ไข และการลบหรือทำให้ไม่ระบุตัวบุคคลตามนโยบายที่ยืนยัน

## 9 External Interface Requirements

### 9.1 Website

- Frontend ใช้ React.js และ Tailwind CSS ตามรายงานต้นทาง
- Backend ให้บริการ API ผ่าน Node.js และ Express.js
- UI ต้องรองรับห้าบทบาทและหลายขนาดหน้าจอ

### 9.2 Database

- ใช้ MySQL เป็นฐานข้อมูลเชิงสัมพันธ์
- ใช้ migration สำหรับควบคุม schema
- phpMyAdmin และ Docker เป็นเครื่องมือสำหรับสภาพแวดล้อมพัฒนา ไม่ถือเป็น interface ของผู้ใช้ปลายทาง

### 9.3 LINE

- ใช้ LINE Official Account และ LINE Messaging API
- ต้องกำหนดเหตุการณ์แจ้งเตือน รูปแบบข้อความ การขอความยินยอม และนโยบายกรณีส่งไม่สำเร็จก่อนพัฒนา

### 9.4 Payment

- ต้องเลือกผู้ให้บริการและกำหนด API, webhook, สถานะ, การหมดเวลา, การยกเลิก และการคืนเงินก่อนพัฒนาโมดูลชำระเงิน

### 9.5 Prediction Service

- ต้องกำหนดว่าโมเดลรันภายในระบบหรือผ่านผู้ให้บริการภายนอก
- ต้องกำหนด input schema, output schema, model version, timeout, fallback และเกณฑ์ความแม่นยำ
- API key ต้องเก็บเป็น secret ภายนอก source code

## 10 กระบวนการหลัก

### 10.1 จองโต๊ะ

1. ลูกค้าเลือกวัน เวลา และจำนวนคน
2. ระบบค้นหาโต๊ะที่ว่างและมีที่นั่งเพียงพอ
3. ลูกค้าเลือกโต๊ะหรือยอมรับโต๊ะที่แนะนำ
4. ระบบตรวจการจองซ้ำอีกครั้งและสร้างรายการ
5. ระบบแสดงเลขอ้างอิงและแจ้งผลผ่าน LINE เมื่อเชื่อมบัญชีแล้ว

### 10.2 สั่งซื้อและเข้าคิว

1. ลูกค้าเลือกประเภทรับประทานที่ร้านล่วงหน้าหรือกลับบ้าน
2. ลูกค้าเลือกเมนูและจำนวน
3. ระบบตรวจสถานะเมนู ราคา และวัตถุดิบ
4. ระบบสร้างคำสั่งซื้อรอชำระและตรึงยอดเงิน
5. ลูกค้าชำระเงินเต็มจำนวน
6. ระบบยืนยันการชำระ ตัดสต๊อก และสร้างรายการคิวครั้งเดียว
7. ระบบส่งอาหารไปคิวครัวและเครื่องดื่มไปคิวเครื่องดื่ม
8. พนักงานรับงาน เปลี่ยนสถานะ และระบบบันทึกเวลา
9. ระบบแจ้งลูกค้าและบันทึกเวลาจริงสำหรับงานวิเคราะห์

### 10.3 คะแนน Walk-in

1. ผู้ดูแลเครื่องดื่มสร้าง QR Code สำหรับรายการที่มีสิทธิ์
2. ลูกค้าสแกนและเข้าสู่บัญชีที่เชื่อม LINE
3. ระบบตรวจอายุ สิทธิ์ และการใช้ซ้ำ
4. ระบบสร้างธุรกรรมคะแนนและแสดงยอดใหม่

## 11 สถานะขั้นต่ำที่ต้องรองรับ

สถานะต่อไปนี้เป็น baseline สำหรับออกแบบ state machine รายละเอียดการย้อนสถานะและสถานะผิดพลาดต้องยืนยันเพิ่มเติม

- Reservation: `pending`, `confirmed`, `seated`, `completed`, `cancelled`, `no_show`
- Order: `draft`, `pending_payment`, `paid`, `in_progress`, `ready`, `completed`, `cancelled`
- Order Item Queue: `waiting`, `in_progress`, `completed`, `cancelled`
- Payment: `pending`, `paid`, `failed`, `expired`, `cancelled`, `refunded`
- Table: `available`, `reserved`, `occupied`, `unavailable`
- Menu Item: `available`, `unavailable`

## 12 ประเด็นที่ต้องยืนยัน

รายการต่อไปนี้มีผลต่อสถาปัตยกรรม กฎธุรกิจ หรือ Acceptance Criteria จึงต้องได้รับคำตอบก่อนเริ่มพัฒนาโมดูลที่เกี่ยวข้อง

1. ร้านเดียวหรือรองรับหลายร้านและหลายสาขา
2. เวลาทำการ วันหยุด และผู้มีสิทธิ์เปลี่ยนสถานะเปิดปิดร้าน
3. ระยะเวลาของช่องจองโต๊ะ เวลาก่อนจองขั้นต่ำ เวลาถือโต๊ะ และกฎ no-show
4. การจองหนึ่งรายการรองรับหลายโต๊ะหรือหนึ่งโต๊ะเท่านั้น
5. ลูกค้ายกเลิกหรือแก้ไขการจองและคำสั่งซื้อได้ถึงขั้นตอนไหน
6. ผู้ให้บริการและช่องทางชำระเงิน รวมถึง timeout การคืนเงิน และค่าธรรมเนียม
7. การชำระเงินของลูกค้า Walk-in และการสั่งที่โต๊ะรวมอยู่ในระบบหรือไม่
8. การตัดสต๊อกเกิดเมื่อชำระเงิน เริ่มทำ หรือเสร็จสิ้น และคืนสต๊อกเมื่อยกเลิกอย่างไร
9. อนุญาตให้สต๊อกติดลบหรือปิดขายอัตโนมัติเมื่อวัตถุดิบไม่พอ
10. กติกาคะแนน อัตราได้รับ วันหมดอายุ ของรางวัล และการคืนคะแนน
11. FIFO เรียงตามเวลาสั่งหรือเวลาชำระ และมีสิทธิ์แทรกคิวเร่งด่วนหรือไม่
12. จุดที่ต้องส่ง LINE notification และข้อความที่ต้องได้รับความยินยอม
13. นิยามรายรับ รายจ่าย ต้นทุน และสูตรกำไรเบื้องต้น
14. จำนวนผู้ใช้พร้อมกัน ปริมาณคำสั่งซื้อสูงสุด และเป้าหมาย response time
15. RPO, RTO, ระยะเวลาเก็บ log และระยะเวลาเก็บข้อมูลส่วนบุคคล
16. วิธีสร้างโมเดล แหล่งข้อมูล ปริมาณข้อมูลขั้นต่ำ ตัวชี้วัด และค่าความแม่นยำที่ยอมรับ
17. อาจารย์หรือเจ้าของโครงงานต้องการใช้ API ของโมเดลภายนอกหรือฝึกโมเดลด้วย Python ภายในโครงการ
18. ขอบเขตการประเมินผู้เชี่ยวชาญและผู้ใช้ รวมถึงจำนวนตัวอย่างจริง

## 13 Definition of Done ระดับระบบ

ระบบถือว่าพร้อมส่งมอบเมื่อ

1. Functional Requirements ที่อยู่ใน release scope มี Acceptance Criteria และผลทดสอบผ่านครบ
2. ไม่มีช่องทางข้ามสิทธิ์ระหว่างห้าบทบาท
3. การจองซ้ำ การยืนยันชำระซ้ำ การตัดสต๊อกซ้ำ และการเพิ่มคะแนนซ้ำถูกป้องกันด้วยการทดสอบ
4. ยอดคำสั่งซื้อ การชำระเงิน รายรับ สต๊อก และคะแนนตรวจสอบย้อนกลับได้
5. กระบวนการหลักทำงานบนคอมพิวเตอร์ สมาร์ตโฟน และแท็บเล็ต
6. LINE และบริการภายนอกมีกรณีทดสอบสำเร็จ ล้มเหลว timeout และ retry
7. มี backup และทดสอบ restore ตามเป้าหมายที่ยืนยัน
8. ข้อมูลเวลาคิวที่ใช้พยากรณ์ครบ ตรวจสอบได้ และไม่มีข้อมูลสำคัญรั่วใน log
9. ผู้แทนของแต่ละบทบาทยอมรับกระบวนการที่เกี่ยวข้องกับตน
10. ประเด็นที่ต้องยืนยันซึ่งกระทบ release ถูกปิดหรือบันทึกเป็นข้อยกเว้นที่ผู้รับผิดชอบอนุมัติ
