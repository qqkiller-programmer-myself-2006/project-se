# Spec ระบบบริหารร้านป้าอ้ออาหารตามสั่ง

Status: ready-for-agent

## Problem Statement

ร้านป้าอ้ออาหารตามสั่งใกล้มหาวิทยาลัยราชภัฏเลย อำเภอเมือง จังหวัดเลย ต้องบริหารโต๊ะ คำสั่งซื้อ ครัว เครื่องดื่ม การเงิน และวัตถุดิบด้วยบุคลากรจำกัด ลูกค้าต้องการทราบสถานะร้าน จอง สั่ง และติดตามเวลารอ ส่วนเจ้าของร้านต้องการข้อมูลประกอบการบริหารที่ตรวจสอบย้อนหลังได้

## Solution

พัฒนาเว็บไซต์ภาษาไทยสำหรับร้านเดียว ใช้ได้ผ่านเบราว์เซอร์และ LINE LIFF ด้วยบัญชีลูกค้าชุดเดียว รองรับห้าบทบาท ได้แก่ ลูกค้า แม่ครัว ผู้ดูแลเครื่องดื่ม Admin และ Owner บัญชีพนักงานหนึ่งบัญชีมีหลายบทบาทได้ ทดลองใช้งานผ่านอินเทอร์เน็ตกับกลุ่มจำกัดก่อน production เต็มรูปแบบ

ข้อกำหนดนี้สังเคราะห์จากหัวข้อ 1.3 ของรายงานและคำตอบ Q1–Q88 ที่ผู้ใช้ยอมรับ การเพิ่ม QR ที่โต๊ะ Guest งานโดยพนักงาน และข้อกำหนดปฏิบัติการเป็นขอบเขตที่ยืนยันเพิ่มเติมระหว่างสัมภาษณ์ ข้อสรุปล่าสุดมีผลเหนือร่าง Requirement ก่อนสัมภาษณ์ สถานะ ready-for-agent หมายถึงพร้อมแบ่งงาน; ประเด็นเปิดท้ายเอกสารต้องปิดก่อนพัฒนาส่วนที่เกี่ยวข้อง

## User Stories

1. ในฐานะลูกค้า ฉันต้องการดูเมนูและสถานะร้านโดยไม่สมัคร เพื่อประเมินว่าจะใช้บริการหรือไม่
2. ในฐานะลูกค้า ฉันต้องการใช้บัญชีเดียวผ่านเว็บและ LINE เพื่อรวมประวัติและคะแนน
3. ในฐานะ Guest ฉันต้องการสั่งด้วยชื่อและเบอร์โทร เพื่อสั่งได้โดยไม่สมัคร
4. ในฐานะ Guest ฉันต้องการผูกคำสั่งซื้อภายใน 24 ชั่วโมงหลังยืนยันเบอร์โทร เพื่อรับประวัติและคะแนนที่ยังไม่ได้รับ
5. ในฐานะลูกค้า ฉันต้องการแก้ข้อมูลหรือขอลบบัญชี เพื่อจัดการข้อมูลของตน
6. ในฐานะลูกค้า ฉันต้องการเห็นโต๊ะว่างและจำนวนคนจริง เพื่อทราบความหนาแน่น
7. ในฐานะสมาชิก ฉันต้องการจองล่วงหน้าและเลือกโต๊ะหรือรับคำแนะนำ เพื่อได้โต๊ะเหมาะกับจำนวนคน
8. ในฐานะสมาชิก ฉันต้องการตรวจและยกเลิกการจองตามกำหนด เพื่อปรับแผน
9. ในฐานะสมาชิก ฉันต้องการ QR เช็กอินและข้อความเตือน เพื่อเข้ารับบริการสะดวก
10. ในฐานะพนักงาน ฉันต้องการสแกนการจองหรือค้นเบอร์โทร เพื่อเช็กอินและเปิดรอบโต๊ะ
11. ในฐานะพนักงาน ฉันต้องการเปิดรอบ Walk-in พร้อมจำนวนคน เพื่อให้ลูกค้าสั่งจากโต๊ะได้
12. ในฐานะพนักงาน ฉันต้องการรายการรอจัดโต๊ะ เพื่อดูแลลูกค้าที่ไม่มีโต๊ะเหมาะสม
13. ในฐานะลูกค้า ฉันต้องการสั่งล่วงหน้าหรือกลับบ้าน เพื่อวางแผนเวลารับอาหาร
14. ในฐานะลูกค้านั่งร้าน ฉันต้องการสแกน QR สั่งและสั่งเพิ่ม เพื่อรับบริการที่โต๊ะ
15. ในฐานะลูกค้าร่วมโต๊ะ ฉันต้องการตะกร้าของตน เพื่อไม่แก้รายการของผู้อื่น
16. ในฐานะพนักงาน ฉันต้องการบันทึกคำสั่งซื้อแทนลูกค้า เพื่อรองรับผู้ไม่ใช้โทรศัพท์
17. ในฐานะลูกค้า ฉันต้องการเลือกขนาด เพิ่มไข่ ความเผ็ด และหมายเหตุ เพื่อสื่อสารความต้องการ
18. ในฐานะลูกค้า ฉันต้องการเห็นราคาที่แน่นอนตอนยืนยัน เพื่อทราบยอดชำระ
19. ในฐานะลูกค้า ฉันต้องการชำระ PromptPay และส่งสลิป เพื่อยืนยันการจ่าย
20. ในฐานะลูกค้านั่งร้าน ฉันต้องการเลือกจ่ายก่อนหรือรวมยอดจ่ายหลัง เพื่อชำระตามความสะดวก
21. ในฐานะพนักงาน ฉันต้องการรับเงินสดและคำนวณเงินทอน เพื่อปิดยอดได้ถูกต้อง
22. ในฐานะลูกค้า ฉันต้องการใบเสร็จอย่างง่าย เพื่อเก็บหลักฐาน
23. ในฐานะ Admin ฉันต้องการตรวจสลิปที่ระบบตรวจไม่ได้ เพื่อให้งานเดินต่อ
24. ในฐานะลูกค้า ฉันต้องการขอยกเลิกและติดตามคืนเงิน เพื่อทราบผลดำเนินการ
25. ในฐานะ Owner ฉันต้องการอนุมัติและบันทึกหลักฐานคืนเงิน เพื่อควบคุมรายจ่าย
26. ในฐานะแม่ครัว ฉันต้องการคิวอาหารและหมายเหตุชัดเจน เพื่อปรุงถูกลำดับ
27. ในฐานะผู้ดูแลเครื่องดื่ม ฉันต้องการคิวของฝ่ายตน เพื่อจัดลำดับการชง
28. ในฐานะพนักงาน ฉันต้องการรับงานและระบุจำนวนที่เสร็จ เพื่อทยอยส่งมอบ
29. ในฐานะพนักงาน ฉันต้องการยืนยันส่งมอบแยกจากทำเสร็จ เพื่อทราบว่าลูกค้าได้รับแล้ว
30. ในฐานะพนักงาน ฉันต้องการเสียงงานใหม่ที่ปิดได้ เพื่อไม่พลาดรายการ
31. ในฐานะผู้มีสิทธิ์ ฉันต้องการสร้างงานทำใหม่หรือเร่งงานพร้อมเหตุผล เพื่อแก้ข้อผิดพลาด
32. ในฐานะลูกค้า ฉันต้องการดูสถานะและเวลารอ เพื่อวางแผนระหว่างรอ
33. ในฐานะ Admin ฉันต้องการตั้งเวลาร้านและปิดชั่วคราว เพื่อควบคุมการรับบริการ
34. ในฐานะ Admin ฉันต้องการตั้งกำลังผลิตครัวและเครื่องดื่ม เพื่อจำกัดงานนัดรับ
35. ในฐานะ Admin ฉันต้องการจัดการโต๊ะ เมนู ตัวเลือก และสูตร เพื่อให้ข้อมูลตรงกับร้าน
36. ในฐานะ Admin ฉันต้องการรับเข้าและปรับสต๊อกพร้อมเหตุผล เพื่อทราบคงเหลือจริง
37. ในฐานะ Admin ฉันต้องการจองวัตถุดิบและหยุดขายเมื่อหมด เพื่อไม่รับงานเกินของที่มี
38. ในฐานะ Admin ฉันต้องการนำเข้า CSV พร้อมตรวจตัวอย่าง เพื่อเตรียมข้อมูลได้เร็ว
39. ในฐานะสมาชิก ฉันต้องการคะแนนเครื่องดื่มและประวัติ เพื่อใช้สิทธิ์สะสม
40. ในฐานะผู้ดูแลเครื่องดื่ม ฉันต้องการออก QR คะแนน Walk-in เพื่อให้คะแนนครั้งเดียว
41. ในฐานะสมาชิก ฉันต้องการแลกคะแนนเป็นเครื่องดื่ม เพื่อใช้รางวัล
42. ในฐานะ Admin ฉันต้องการตั้งรางวัลและจำนวนสิทธิ์ เพื่อควบคุมการแลก
43. ในฐานะ Admin ฉันต้องการบันทึกรายจ่ายจริง เพื่อสรุปการเงิน
44. ในฐานะ Owner ฉันต้องการแยกต้นทุนประมาณการกับรายจ่ายจริง เพื่อไม่หักต้นทุนซ้ำ
45. ในฐานะ Owner ฉันต้องการรายงานยอดขายตามวัน เดือน ปี เพื่อวิเคราะห์ร้าน
46. ในฐานะ Owner ฉันต้องการเมนูขายดี เวลาหนาแน่น โต๊ะและคิว เพื่อวางแผนบริการ
47. ในฐานะ Owner ฉันต้องการส่งออก CSV เพื่อวิเคราะห์ต่อ
48. ในฐานะ Owner ฉันต้องการจัดการพนักงานและบทบาท เพื่อควบคุมสิทธิ์
49. ในฐานะ Owner ฉันต้องการประวัติรายการสำคัญและแจ้งเหตุผิดปกติ เพื่อกำกับร้าน
50. ในฐานะลูกค้า ฉันต้องการติดตามเว็บได้เมื่อ LINE ส่งไม่สำเร็จ เพื่อไม่ขาดข้อมูล
51. ในฐานะ Owner ฉันต้องการสำรองและกู้ข้อมูล เพื่อกลับมาให้บริการเมื่อระบบเสีย
52. ในฐานะ Owner ฉันต้องการเห็นผลโมเดลเทียบ baseline เพื่อประเมินความน่าเชื่อถือ
53. ในฐานะผู้ประเมิน ฉันต้องการสถานการณ์ทดสอบครบแต่ละบทบาท เพื่อประเมินโครงงานจากหลักฐาน

## Implementation Decisions

### D01 บัญชีและสิทธิ์ — Q1–Q3, Q7–Q9, Q16, Q22, Q31, Q38, Q41, Q56–Q59

- สมาชิกจองและสะสมคะแนนได้; Guest ดูเมนูและสั่งได้ด้วยชื่อและโทรศัพท์ ผูกคำสั่งซื้อภายใน 24 ชั่วโมงโดยพิสูจน์ว่าเป็นเจ้าของเบอร์เดียวกันและไม่ให้คะแนนซ้ำ
- ลูกค้าหนึ่งบัญชีเชื่อม LINE ได้หนึ่งบัญชี การรวมบัญชีต้องยืนยันตัวตน ชื่อและโทรศัพท์เป็นข้อมูลหลัก อีเมล optional
- Owner สร้าง ปิดบัญชี และกำหนดหลายบทบาท พนักงานใช้ชื่อผู้ใช้/รหัสผ่าน เปลี่ยนรหัสตนเองได้ Owner รีเซ็ตได้ ต้อง hash รหัสและจำกัดการลองผิด
- Owner มีสิทธิ์ Admin ทั้งหมด พร้อมอนุมัติคืนเงินและปรับยอดย้อนหลัง อ่าน audit และจัดการพนักงาน Admin ไม่เปลี่ยนหรือปิด Owner
- แม่ครัวและเครื่องดื่มทำงานตามบทบาทที่ได้รับและสร้างรายการทำใหม่ในฝ่ายตนได้ บันทึกผู้ลงมือทุกครั้ง
- ลูกค้าขอลบบัญชีได้ ถอนการเชื่อม LINE และทำข้อมูลส่วนบุคคลในประวัติเป็นนิรนาม การเงินยังคงตรวจสอบได้

### D02 ร้าน โต๊ะ และการจอง — Q2, Q6, Q9–Q10, Q15, Q17–Q18, Q32, Q42, Q51–Q52, Q72, Q81

- ร้านเดียว สาขาเดียว ตารางเวลาเปิดประจำสัปดาห์และคำสั่ง Admin ปิดชั่วคราวพร้อมเหตุผล/เวลาเปิดคาดหมาย คำสั่งชั่วคราวมีผลเหนือกำหนดเวลา เก็บประวัติ
- การปิดร้านไม่ยกเลิกงานเดิมอัตโนมัติ แสดงรายการกระทบให้ Admin ตัดสินใจและแจ้งลูกค้า
- จองได้ไม่เกิน 3 วัน ต้องก่อนนัดอย่างน้อย 60 นาที ยกเลิกเองก่อนนัดอย่างน้อย 60 นาที ถือโต๊ะ 15 นาที ไม่เก็บมัดจำ หนึ่งการจองหนึ่งโต๊ะ
- เลือกโต๊ะเองหรือรับคำแนะนำโต๊ะว่างขนาดเล็กที่สุดที่จุได้ ตรวจการจองทับซ้อนแบบ atomic
- เช็กอินจาก QR การจองหรือค้นโทรศัพท์ ตรวจจำนวนคนและเปิดรอบโต๊ะ จำนวนคนเปลี่ยนได้ ถ้าโต๊ะไม่พอให้แนะนำใหม่หรือรอจัดโต๊ะ
- Walk-in เลือกโต๊ะ ระบุจำนวนคน แล้วเปิดรอบหนึ่งครั้ง; ถ้าเต็มเข้ารายการรอจัดโต๊ะ แยกจากคิวปรุง
- QR โต๊ะรับคำสั่งซื้อเฉพาะรอบที่เปิดอยู่ หลายคนใช้พร้อมกันได้ด้วยตะกร้าแยก สั่งเพิ่มเป็นคำสั่งซื้อใหม่ในรอบเดิม ปิดรอบโดยพนักงานเมื่อยอดครบ
- จำนวนผู้ใช้บริการนับคนจริงที่กำลังใช้บริการ ไม่ใช่จำนวนที่นั่งสูงสุด
- เตือนการจองก่อน 30 นาทีพร้อม QR และรายละเอียด ปุ่มยกเลิกแสดงเฉพาะเมื่อยังอยู่ในเวลาที่อนุญาต

### D03 เมนูและคำสั่งซื้อ — Q3, Q19–Q20, Q25–Q26, Q33, Q44–Q47, Q54, Q71

- รองรับจองพร้อมสั่งล่วงหน้า กลับบ้าน QR ที่โต๊ะ และพนักงานสั่งแทน แยกช่องทางสร้างออกจากประเภทรับบริการ
- เมนูมีรายละเอียด รูป ราคา หมวด สถานะ ตัวเลือกขนาด/เพิ่มราคา ความต้องการเฉพาะไม่เพิ่มราคา และหมายเหตุจำกัดความยาวที่เห็นชัดในครัว
- ตอนยืนยันตรวจราคาและสต๊อก ตรึงราคาเมนูและตัวเลือกกับรายการที่ยืนยัน การเปลี่ยนราคามีผลต่อตะกร้าและคำสั่งซื้อใหม่
- เมนูขายได้เมื่อ Admin เปิดขายและสูตรมีสต๊อกพร้อมขายเพียงพอ
- ล่วงหน้าเลือกช่วง 15 นาที จำกัดจำนวนงานแยกสองฝ่าย ตั้งค่าโดย Admin เมื่อเต็มเสนอช่วงถัดไป
- ก่อนชำระแก้ได้เฉพาะส่วนที่ยังไม่เริ่มทำ; คำสั่งซื้อจ่ายหลังที่ร้านยืนยันแล้วต้องใช้การแก้ไขผ่านผู้มีสิทธิ์ ไม่แก้งานเริ่มทำย้อนหลัง

### แนวทดสอบที่เสนอ

ใช้หน้าจอและ application API เป็น seam หลัก ตรวจผลที่ผู้ใช้สังเกตได้ และผลข้าม module เช่น รับเงินแล้วเกิดคิว/รายรับครั้งเดียว ไม่ยึดโครงสร้างภายใน ทดสอบฐานข้อมูลด้วย transaction จริงในสภาพแวดล้อมทดสอบ; LINE, SlipOK, EasySlip และพยากรณ์ใช้ adapter จำลองที่ให้ผลสำเร็จ ล้มเหลว timeout และตอบซ้ำได้ ตรวจสัญญากับบริการจริงแยกก่อน pilot ตามสิทธิ์และโควตาที่มี

ยังไม่มีโค้ดหรือชุดทดสอบเดิมให้ใช้อ้างอิง ไม่ถือว่ามีการทดสอบผ่านแล้ว แนว seam นี้เสนอให้ผู้ใช้ทบทวนก่อนแบ่ง ticket implementation

### Acceptance scenarios

- AT01: Guest สั่งได้ แต่จอง/คะแนนต้องมีบัญชี การผูกซ้ำหรือใช้เบอร์คนอื่นไม่ได้
- AT02: บัญชีเดียวข้ามเว็บ/LIFF เห็นประวัติเดียวกัน; ผู้ไม่มีบทบาทเรียก API ที่จำกัดไม่ได้
- AT03: การจองโต๊ะเวลาเดียวกันพร้อมกันสำเร็จได้ครั้งเดียว ทดสอบขอบ 3 วัน/60 นาที/15 นาทีด้วยนาฬิกาควบคุม
- AT04: เช็กอินเปิดรอบเดียว จำนวนคนจริงอัปเดต QR รอบปิดรับคำสั่งซื้อไม่ได้
- AT05: ลูกค้าหลายคนมีตะกร้าแยก สั่งเพิ่มไม่แก้งานเดิม และรวมเฉพาะยอดค้างตอนปิดโต๊ะ
- AT06: ล่วงหน้า/กลับบ้านไม่พร้อมทำก่อนจ่าย; นั่งร้านจ่ายหลังพร้อมทำเมื่อพนักงานยืนยัน
- AT07: สลิปถูกยืนยันแล้วเกิดผลครั้งเดียว สลิปผิดยอด/ผู้รับ/ซ้ำถูกปฏิเสธ timeout รอตรวจ
- AT08: เงินสดทอนถูก ใบเสร็จไม่ซ้ำ คืนบางส่วนไม่เกินยอดและไม่คืนยอดยังไม่ชำระ
- AT09: แข่งวัตถุดิบชิ้นสุดท้ายสำเร็จหนึ่งราย จองก่อนชำระ เริ่มทำตัดครั้งเดียว ยกเลิกคืนยอดจอง
- AT10: คิวแยกฝ่าย เรียงพร้อมทำ คำสั่งล่วงหน้าไม่เริ่มทันทีที่จ่าย; แทรกคิวต้องมีสิทธิ์และเหตุผล
- AT11: จำนวนเสร็จไม่เกินจำนวนงาน ทำเสร็จกับส่งมอบแยกกัน ตัวเลือกต่างกันไม่ถูกรวมผิด
- AT12: ราคาเก่าของรายการยืนยันไม่เปลี่ยนตามเมนู งานทำใหม่ไม่คิดเงินซ้ำ
- AT13: คะแนน/QR ใช้ซ้ำไม่ได้ แลกพร้อมกันไม่ใช้คะแนนเกิน ยกเลิกคืนสิทธิ์ตามสถานะ
- AT14: ยอดรับ คืน รายจ่าย กำไรและ CSV กระทบยอดตรงกัน ต้นทุนประมาณการไม่ถูกหักซ้ำ
- AT15: LINE ล้มเหลวไม่ยกเลิกงานและ retry ไม่ส่งซ้ำไม่สิ้นสุด แจ้งครบงานครั้งเดียว
- AT16: reconnect ตรวจสถานะใหม่และไม่รับคำสั่งเก่าทับงานที่เสร็จแล้ว
- AT17: CSV ผิดแสดงข้อผิดพลาดก่อนบันทึก การนำเข้าต้องมีผลที่ตรวจสอบได้
- AT18: ประเมิน ML ตามเวลา ไม่มี feature อนาคต โมเดลไม่ดีกว่า baseline ใช้ fallback
- AT19: ทดสอบภาระตาม D10 บันทึกเครื่อง เครือข่าย ข้อมูลและ percentile แยกเวลา provider
- AT20: ตรวจหน้าจอมือถือ/แท็บเล็ต/คอมพิวเตอร์ keyboard contrast และข้อความผิดพลาด
- AT21: สำรองและ restore กับข้อมูลตัวอย่าง ตรวจ RPO/RTO และแจ้ง Owner เมื่อ backup ล้มเหลว
- AT22: ลบบัญชีแล้วข้อมูลระบุคนหายจากการใช้งาน แต่ยอดการเงินยังถูกต้อง งานล้างข้อมูลตามอายุทำงาน

### การประเมินโครงงาน

ตัวแทนลูกค้า แม่ครัว เครื่องดื่ม Admin และ Owner ทดลอง happy path และกรณีผิดพลาด ผู้เชี่ยวชาญเป้าหมาย 3–5 คน จำนวนผู้ใช้คำนวณจากประชากรที่เข้าถึงจริง ไม่ใช้ 390 คนโดยไม่มีที่มา ประเมินความถูกต้อง ความเร็วและความพึงพอใจ แสดงผลจากหลักฐานจริงเท่านั้น

## Out of Scope

หลายร้าน/สาขา Delivery และคนส่ง การจัดซื้อจากซัพพลายเออร์ เงินเดือน/ตารางกะ/ลงเวลา ระบบบัญชีภาษีเต็มรูปแบบ ใบกำกับภาษี แยกบิลรายคน โปรโมชันทั่วไป offline เต็มรูปแบบ ภาษาที่สอง การพัฒนา LLM เอง และ PDF รายงานตกแต่ง

## Further Notes

### ลำดับส่งมอบที่ยืนยัน — Q88

1. Release 1: บัญชี บทบาท เมนู โต๊ะ รอบโต๊ะ คำสั่งซื้อ เงินสด คิว
2. Release 2: การจอง ล่วงหน้า กลับบ้าน PromptPay และ LINE
3. Release 3: วัตถุดิบ สูตร สต๊อก คะแนน รางวัล การเงิน Dashboard และ CSV
4. Release 4: baseline ข้อมูลจริง โมเดลและการประเมิน ก่อนเปิดพยากรณ์

ข้อพึ่งพาที่ต้องสะท้อนใน ticket: การป้องกันขายเกินและจองสต๊อกเป็นเกณฑ์ของ flow ออนไลน์ แม้หน้าบริหารสต๊อกอยู่ Release 3 จึงต้องเตรียมแกนสูตร/จองสต๊อกก่อนเปิด pilot ที่อ้างว่าป้องกันขายเกิน เก็บเวลาคิวตั้งแต่ Release 1 เพื่อสะสมข้อมูล Release 4

### ประเด็นที่ยังไม่เคยตัดสินจากการสัมภาษณ์

อย่าถือการตอบ “ตามคำแนะนำ” เป็นคำตอบของประเด็นใหม่ต่อไปนี้ ให้ปิดใน ticket ที่เกี่ยวข้องก่อน implementation:

- ช่วงเวลาครองโต๊ะและเวลาทำความสะอาดที่ใช้ตรวจการจองซ้อน รวมกฎต่อเวลาหรือย้ายโต๊ะ
- อายุการกันสต๊อกระหว่างรอจ่าย/ตรวจด้วยมือ และการรับเงินที่มาถึงหลังหมดอายุ
- วิธีพิสูจน์โทรศัพท์ลูกค้าและต้นทุน OTP; วิธี Guest เข้าถึงคำสั่งซื้ออย่างปลอดภัย
- QR โต๊ะคงที่พร้อมสถานะเปิดอย่างเดียวไม่กันคนที่เคยถ่าย QR ไว้ ต้องเลือกกลไกจำกัดสิทธิ์ในรอบโต๊ะโดยรักษาภาระพนักงานต่ำ
- คะแนนที่ใช้ไปแล้วก่อนคืนเงินจะติดลบหรือหักสิทธิ์อย่างไร และรางวัลราคา 0 ได้คะแนนหรือไม่
- สูตรคำนวณ lead time รวมคิวรอ และน้ำหนักงานจำนวนมากต่อ capacity 15 นาที
- การนับยอดขายรายวันตามเวลารับเงินหรือส่งมอบ นิยามจำนวนคำสั่งซื้อเมื่อตัดบางรายการ และเวลา cutoff ปิดยอด
- เกณฑ์ช่วงสลิปที่ยอมรับ ค่า timeout/retry ระยะงดแจ้งซ้ำ และช่องทางแจ้ง Owner
- วิธีสร้างช่วงพยากรณ์และความเชื่อมั่น การวัดจำนวนคนปฏิบัติงานโดยไม่มีระบบกะ
- ผู้ให้บริการ hosting/model และ provider ที่ใช้ใน pilot ยังไม่เลือก; ต้องตรวจสัญญาบริการและค่าบริการก่อนใช้จริง

D01 ครอบคลุมบัญชี/สิทธิ์; D02 ร้าน/จอง; D03 เมนู/คำสั่งซื้อ; D04 การเงินชำระ; D05 คิว; D06 สต๊อก; D07 คะแนน; D08 รายงาน/แจ้งเตือน; D09 ML; D10 คุณภาพ/ข้อมูล โดยเลข Q ในแต่ละหัวข้อผูกกลับกับการสัมภาษณ์ Q1–Q88
